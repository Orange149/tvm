# 集中上板与恢复

助手负责运行电脑端入口，用户仅在每次有效启动完成后手动重启并告知联网。有效实验十次启动：2 次标定、2 次筛选、6 次确认；本地准备和预检不计入。

首先执行 `prepare` 和 `validate`。准备包保留全部 172 个模块、原运行库、输入、参考、位流和驱动，仅编译新执行器；`OFFLINE_READINESS.json` 必须为 `PREPARED_OFFLINE`。这个状态不代表已通过板端正确性或性能验证。

`board run --execute-board` 创建批次，`board resume --execute-board` 接续。每次启动先确认已经授权的 `/dev/mmcblk1p3` UUID 并挂载到现有实验目录；与主实验共用板端会话锁。部署不在板端存放传输压缩包。任务回收在本地验证和持久化后清理板端大文件，保留任务身份墓碑。

每次运行前后同步、清除文件缓存并校验完整部署清单。若出现哈希异常，程序停止。此前开发板曾出现跨启动文件损坏，根因仍未确定；异常副本须先保留，只能恢复与本轮冻结包相同的字节，重新完整校验后再继续，不能重新标定或替换参考来掩盖损坏。

程序在当前启动执行全部计划工作后进入 `WAITING_NEW_BOOT`。助手确认原始文件已回收、数据同步、板端没有活动会话后通知用户重启。相同 boot ID 续跑只返回等待，不会进入下一次独立启动。程序从不发送 reboot 或 shutdown。

断线或电脑端进程退出时直接执行 resume。仍在运行的板端任务受锁保护，恢复期间仅轻量查询；不会部署、打包或回收活动窗口。恢复读取相同任务哈希、执行模式和 boot ID。已接受的窗口不重复测量；未完成启动若已经换 boot ID，则整个启动作废并以新启动替换，失败记录继续保留。

`status` 可随时在电脑端检查启动数和当前状态。两次标定后，电脑可能需要较长时间完整枚举四核约 1.83 亿配置；板端此时没有测量任务，不将电脑搜索时间纳入性能。筛选后冻结文件，再开始六次确认，不允许确认结果反向调整选点。

十次启动完成后 `analyze` 校验各阶段凭据、原始文件与独立性，输出 `analysis/REPORT_zh.txt`、方法和逐启动 CSV、阶段加速曲线、固定划分图、机制与历史对照。缺少六次完整确认时拒绝正式分析。
