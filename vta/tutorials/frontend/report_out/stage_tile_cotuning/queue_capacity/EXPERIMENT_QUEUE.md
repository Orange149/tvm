|---|---:|---:|---:|---:|
| A | 15 | 5312 | 2792 | 77151232 |
| B | 14 | 5312 | 2792 | 77394432 |
| C | 15 | 5312 | 2792 | 77326848 |

四拓扑各 default_off/default_diag 两模式，共 256 正式帧逐字节通过。
所有提交均 explicit_sync，没有 legacy_auto_sync；每个进程观察到一个 CommandQueue 实例。
两模式池内高水位一致且 warmup 后不增长。profiler 汇总的调用数/张量字节/指令数一致。
现有 profiler 的通用 MemCopyFromHost 计数**不包含**本轮直接调用驱动的队列复制，不能据其零值称没有复制。

按两倍峰值、至少 4 KiB、向上 256 B 对齐：指令 10752 B、微指令 5632 B，合计 16384 B。
相对两块各 32 MiB，预测每进程减少 67092480 B，Q1 已逐字节核验。

| A | 77151232 | 10058752 | 67092480 | 86.9623% |

这些对比的两侧都开启已有借池方案，不能把借池节省重复计入队列节省。

## 指令准备时间：仅诊断，非 FPS

诊断均值（包含两帧 warmup）：四拓扑每帧微指令拼接约 0.114–0.162 ms，
两类队列复制合计约 0.309–0.339 ms，VTADeviceRun 合计约 59.09–60.48 ms。
这些是带诊断的分项测量，不是稳态 FPS；device_run 包含 MMIO/设备执行/轮询，不能当作 DMA 等待。
queue_cache_us 包含分支/计时开销，本配置 coherent 路径并未调用实际队列 cache flush。
现有 enqueue 计时属于调用内耗时，未来若出现 AutoSync 必须处理其嵌套关系，不能直接和设备时间相加。

## 验证与缺口

基础容量策略 C++ 19 项检查通过；初轮 Python 14 个 test methods 通过（包括包装的
19 项容量检查、原 23 项共享缓冲 native 检查和 10 项 storage 审计测试）。
补充多 island 批次多重集合检查后，当前 15 个 methods 通过；另有既有 33 个
handoff/once-quant/shared-edge/compile-context/segment-counter 回归通过。
这些不是依赖/缓存跨批正确性测试，Q2 不因此放行。

Q1 要求默认与缩容：逐帧输出一致、提交批次数及字节一致、张量流量计数一致、
实际节省逐字节符合预测、steady state 不增长。生产路径容量拒绝及 4000 帧自然压力已通过。

Q2 特别风险：DepPush 可回写末条指令，DepPop 可延迟绑定下一条指令；
仅看当前指令条数或单帧输出最后使用不构成安全切批点。
Synchronize 会清除微指令缓存并重置索引；跨批引用/依赖必须另测。
本轮没有修改同步阈值、tile、VTA 指令语义或硬件，没有声称发现容量—吞吐拐点。

后续 Q2 必须先验证的条件（均尚未资格化）：

- 候选 API 边界的四条依赖通道闭合，且没有延迟 pending pop；不能只检查净计数而忽视执行依赖。
- FINISH 前 load/compute/store 全部完成，下一批读用的 inp/wgt/acc SRAM 内容仍有效。
- 微指令 reset 后全部后续引用重新绑定正确，地址不会指向失效序列化内容。
- 单 VTA 互斥覆盖整个 stage，不能在提前提交后让另一 island 插入并覆盖仍存活的 SRAM。
- capture/replay 与多批次的关系单独处理；当前仅对其复制前容量加防护，没有完成重放回归。

因此 16 KiB 是本轮带余量的候选，不是最小可执行容量或最终 F。
未证明提前提交安全前，保留 fail-closed 接口，不用硬件 hang 试错寻找边界。
