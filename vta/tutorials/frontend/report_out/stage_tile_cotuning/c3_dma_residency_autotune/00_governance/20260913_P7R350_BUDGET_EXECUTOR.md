# P7R350：逐点构建的预算执行器

P7R349 发现整前沿预构建提前支付了未必必要的第二候选成本，且分阶段求和缺少外层编排时间。
本轮新增 `run_vta_budgeted_process_plan.py`，实现下一轮真实实验所需的执行与计时基础。
这是本地工具验证，不增加板端候选池、前瞻 holdout 或搜索加速证据。

## 执行行为

输入为预先冻结的 JSON 计划：有限正数 `budget_seconds`、固定步骤顺序、argv 字符串数组、
绝对 cwd、候选 ID，以及测量结束时必须新生成的结果凭据。执行器不使用 shell 展开命令，
不读取 oracle，也不根据已有最优 latency 决定停止。

共同 prepare 步骤必须放在所有候选之前；每个候选必须按 build→measure 执行，完成后才允许
下一候选 build。这样同一候选的模型准备、导入、编译和子进程启动成本会进入共享单调时钟。
把远程 clean start、上传、分配、正确性与测量放入 measure 子进程时，其外层耗时也会一并计入。

预算是步骤准入预算：已经达到预算便不再启动新步骤。活动步骤自然结束，记录 overrun；
超预算完成的标签不得进入预算内候选集合。这样避免为满足严格截止时间而中断 VTA 操作，
同时不会把超支隐去。预算内完成、预算外完成、失败和未开始步骤分别留有记录。

完成凭据必须与候选身份和计划要求一致、且执行前不存在；退出码 0 本身不等于通过验证。
结果凭据是否代表三 seed FPGA-correct，需要由后续真实 measurement adapter 和冻结合同定义。
执行器提供的是完成凭据门，不会凭空证明计算正确性。

## 计时边界

时钟从 wrapper 源码入口开始，早于读取计划、校验、创建输出和任何昂贵子进程导入；计入
每一步子进程的整个生命周期、结果凭据读取和中间日志写入。Python 解释器启动和最终报告
序列化仍在边界外，文档与结果中明确说明。不能拿本地 fixture 的时间声称已测完整真实调优墙钟。

## 测试与结果

6 项测试通过：超预算测量计费但标签不准入；构建失败不启动测量；准备阶段已用完预算不启动
子进程；拒绝整前沿预构建顺序和候选身份不匹配；真实子进程生成新凭据且拒绝旧凭据；
退出 0 但缺少凭据仍失败。测试报告和源码 SHA-256 位于
`07_grouped_holdout/20260913_p7r350_budgeted_process_executor_local_run01/`。

下一步将单候选真实模型构建器与板端结果 adapter 接入，冻结未见 workload 的预算与
Random/bytes/calls/前沿顺序，再比较预算内可用配置质量、实际 elapsed 与 overrun。
本轮没有连接开发板，没有执行任何模型候选，没有产生 latency 标签。
