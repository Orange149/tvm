# R18-H1 T8 P1/P2 部分权重驻留本地资格

日期：2026-09-23。状态：`LOCAL_MECHANISM_VALID_BUT_UOP_GATE_NOT_MET`。

## 结论

P1-S/P2-S 已按预定边界完成本地实现和资格检查：保持 R18-H1 T8、双输出虚拟线程、mode 8 的循环与
计算顺序、首次需要装载、单提交和零额外 drain。P1-S 保留一个归约组、P2-S 保留两个归约组，其余组
共享一个流式 WGT 槽。

两种程序均通过最终地址和依赖审计、三 seed FSim 逐元素精确校验，以及同一参数句柄连续更换权重的
多次调用。但它们没有实现本轮最重要的 UOP 门槛：P1-S、P2-S 与 P4-S 的累计 UOP LOAD 均为
1,624 B。因此不冻结上板候选。

## 实现与安全边界

实验 pass 只接受 P1/P2 和 R18-H1 T8 的四组零基、静态展开归约。每个虚拟线程的地址布局为：

- 前 P 个组使用互不覆盖的固定驻留槽，只在第一个空间块装载；
- 其余组共享紧随驻留区的一个流式槽，在每个空间块按原顺序重新装载；
- GEMM 的 WGT 地址与对应 LOAD 使用同一映射；
- 不插入同步、drain 或额外提交；
- 形状、循环、源布局或 compact allocation 不匹配时 fail-closed。

P1-S/P2-S 的 INP 请求均与 O2/P4-S 相同，为 487,424 B/56 次；输出请求、计算语义和函数结束同步也
保持一致。最终地址审计通过，单个 UOP kernel 最大为48条，运行期有效 UOP 占用峰值仍为 unknown。

## 为什么少驻留没有降低 UOP

mode 8 为满足 VTA runtime 的单整数 cached-UOP 签名约束，仍需将四个外层归约组静态展开。部分组共享
流式 WGT 地址并不会自动合并这些展开后的 GEMM kernel；最终命令中 P1/P2/P4 仍装载同样的累计 UOP。
因此“减少固定驻留组数会换来更简单 μop 组织”的假设在当前 lowering 下不成立。

P1/P2 确实比 O2 少一些权重请求和指令，但相对 P4-S 没有 UOP 或启动前置请求优势，同时分别增加
165,888 B 和110,592 B权重请求。按预注册规则，这不足以进入板端性能测试。

下一步不应直接扩大部分驻留容量搜索。若继续攻克这一点，需要先改变 UOP 模板生成，使共享流式地址的
归约组实际复用同一 kernel；否则当前 P4-S 在这一层严格拥有更少的权重请求和指令，而 UOP 代价相同。
论文主证据可优先使用 Y00 双启动正结果说明“传输压力决定驻留收益”，并把本实验作为“驻留粒度必须与
可实现的 μop 模板联合选择”的边界证据。
